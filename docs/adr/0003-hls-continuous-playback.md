# Playback becomes one continuous HLS source, not a JS-driven chunk queue

A Book currently plays as a sequence of short chunks (`chunkText.js`, `maxChars = 200`, at most 4 Sentences) through the ping-pong pair of `<audio>` elements in `useBookPlayer.js`: one element plays while the other preloads the next chunk, and at every chunk boundary `handleEnded` swaps them and calls `.play()` on the newly active element. Sentence highlighting sits on top of that, mapping `audio.currentTime` against per-chunk spans derived from edge-tts word boundaries (`sentenceSpans.js`, consumed through `findActiveSentenceIndex`).

Backgrounding breaks this, and two phases of work have not fixed it. Phase 1.8 added MediaSession registration, a foreground-resync reconciliation checkpoint, and a single-active-audio invariant. Phase 1.9 ticket 04 added a stall retry after diagnostics showed the active element reporting `paused === false` while `currentTime` sat at exactly 0 across multiple reconciliation checkpoints. Playback still does not reliably survive an app switch.

We are replacing the chunk queue with a single continuous source. One `<audio>` element takes an EVENT-type `.m3u8` playlist as its `src`, and that playlist gains segments as TTS generation proceeds, so a Book is still narrated progressively rather than after a whole-book synthesis. Segment advancement happens inside the browser's media stack, so no application code runs at a segment boundary at all. Sentence identity comes from a book-level WebVTT metadata track (`<track kind="metadata">` with `track.mode = 'hidden'`), read off `track.activeCues[0].id` in a `cuechange` handler, which replaces the `currentTime`-to-span lookup outright.

**The spike, and the correction it forced.** A throwaway spike (`public/hls-spike/` on branch `hls-spike`, deleted after the fact) served a static 600s VOD playlist of 21 x 30s fMP4 segments alongside a 120-cue VTT, logging wall-clock time against `audio.currentTime` on a 1s heartbeat. Measured on a physical iPhone: in a Safari tab, 388s backgrounded advanced audio by 387.3s (99.8%, 12 segment boundaries crossed unattended); launched from the home screen in standalone mode, 340s backgrounded advanced audio by 340.0s (100.0%, 11 boundaries). The metadata track stayed exactly aligned across all of it - at `currentTime` 359.7s the active cue was `s-71`, whose span is 355-360s, with no reconciliation code of any kind in the page.

The same spike refuted the mechanism we had assumed. We expected the current player to fail because iOS freezes a hidden page's JS, leaving `handleEnded` unable to run at the boundary. The heartbeat would have logged any freeze longer than 2.5s; it logged none in either run, and in the tab run the page was still writing log entries 12s after being hidden. **JS was never frozen.** The real failure condition is therefore not "no code runs at the boundary" but "a `.play()` call on a freshly-loaded element in the background produces no audio" - which is precisely what the Phase 1.9 diagnostic recorded as `paused === false` with `currentTime` stuck at 0, and what its stall retry was papering over.

That distinction is what makes HLS the fix rather than one option among several. The requirement is not to survive a frozen main thread; it is to never need a second `.play()` after the initial user gesture. A single continuous source satisfies that by construction.

**What this removes.** The ping-pong pair and everything that exists to police it: `activeIsPrimary`, `enforceSingleActiveAudio`, and the chunk-advance path in `handleEnded`. The stall detection added for the symptom rather than the cause, including `STALL_GRACE_MS`, `activePlayAttemptAtRef`, and the `currentTime === 0` check. The whole time-to-Sentence mapping in the hook: `findActiveSentenceIndex`, `handleTimeUpdate`, and the `currentSentenceSpans` memo. The Phase 1.9 ticket 04 diagnostics currently marked TEMPORARY. And the dead `currentTimeSeconds` state, which is written in three places and never read. `deriveSentenceSpans` survives, but moves server-side into VTT generation. The one write to `audio.currentTime` that stays is `applySeek`, which is Sentence-click seeking and has nothing to do with backgrounding.

Because the VTT is generated per Book with absolute times - the server knows each segment's real duration when it assembles the playlist - the client does no cumulative-offset arithmetic. Deferring the highlight change to a later phase would mean threading those offsets through `applySeek` and the span lookup as interim work, only to delete it; the two changes are cheaper together than in sequence, and are scoped as one phase for that reason.

Considered alternatives: raising `maxChars` so chunks are longer (rejected - it reduces how many `.play()` calls happen but not that they happen, so it is palliative once the failure condition is understood); one long audio file per Book (rejected - it does eliminate the second `.play()`, but playback could not start until the entire Book was synthesized, which gives up progressive narration); Media Source Extensions or ManagedMediaSource (rejected - it also yields one continuous element, but appending buffers is itself application code, and iOS support starts at 17.1 where native HLS does not); Web Audio scheduling with per-Sentence `AudioBufferSourceNode`s (rejected - it would give Sentence identity for free and pre-schedule across boundaries, but iOS suspends a backgrounded `AudioContext` more aggressively than it does `<audio>`, and it forfeits the MediaSession lock-screen treatment, so it makes the reported problem worse); in-stream ID3 timed metadata instead of a sidecar VTT (rejected for now - it removes even the need to author cue times, but the server already knows each Sentence's offset when it stitches segments, so the extra machinery buys nothing here); dropping to chunk-level highlighting and deleting all timing logic (rejected - simplest of all, but a UX regression); a native wrapper with a real background-audio entitlement (rejected for this phase - it is the Phase 2 direction and carries the unresolved edge-tts AGPL question).

**What the spike did not establish.** It served a static VOD playlist, not the EVENT playlist that progressive generation requires, so appending segments to a playlist mid-playback is unproven. Its VTT was same-origin with the audio, so `<track>` behaviour when audio lives on Vercel Blob - CORS headers plus `crossorigin` on the element - still needs checking. It covered iOS only, since that is where the problem was reported. And it observed that `activeCues` is correct whenever read, not that `cuechange` fires while backgrounded; the design depends only on the former.
