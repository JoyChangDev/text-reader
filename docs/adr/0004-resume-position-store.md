# The resume position lives in Redis, with Blob as a snapshot rather than the source of truth

The resume position was a field on the `library/index` blob, rewritten in full every time the active Sentence changed. That put a counter which moves every few seconds inside a document that otherwise changes only when a Book is added or removed, which cost an Advanced Operation per Sentence (2,000 a month on Hobby — under six hours of listening) and left every save in a read-modify-write race with `addBook` and `deleteBook`. We split the two: the position moves to Redis as three numeric fields per Book under one `library:resume` hash, written by a Lua script that stores only if the incoming `updatedAt` is newer than the stored one. Vercel Blob keeps a per-Book snapshot at `library/<bookId>/resume`, written only at the backgrounding flush points.

**This inverts ticket 08's arrangement, deliberately.** The Chunk index treats Redis as a pure cache because the per-Chunk Blob metadata is authoritative and an evicted index can simply be rebuilt. A resume position has no second copy to rebuild from, so something has to be authoritative and Redis is the only store on the live write path. The snapshot bounds the loss to one session instead of everything, which is why it is written at the flush points rather than never — but it is a backstop, not a second source of truth, and Redis wins whenever it answers.

`updatedAt` is stamped on the client, at the moment reading reached that position, rather than on the server when the request arrives. Ordering by arrival is correct only while every device is online; Phase 2's offline whole-Book downloads make "a device flushes an hour-old position after regaining network" routine, and under arrival ordering that stale position wins. The comparison is a script rather than a read followed by a conditional write because Upstash's REST API has no `WATCH`, so nothing else is atomic.

Considered alternatives: keeping the position in Blob and writing only at the flush points (rejected — fixes the quota and leaves the lost update exactly where it is, and makes the position up to a whole session stale on a crash); moving the whole index into Redis under one key with `GET`/`SET` (rejected — reproduces the read-modify-write race byte for byte; the problem was never where the data lived but that one shared document was rewritten to change one field); resolving conflicts by keeping the highest Sentence ordinal instead of the newest timestamp (rejected — it needs no new field and `sentenceOrdinals.js` already gives a total order, but it would permanently refuse a Listener who deliberately seeks backwards to re-hear something); throttling the write instead of moving it (rejected as a fix on its own — Sentences already advance about every ten seconds, so even a generous throttle buys under 2× against a roughly 50× shortfall); dropping the server-side position for `localStorage` (rejected — cross-device resume is a shipped feature).

**What this does not decide.** The same Book open on two online devices is still last-write-wins, now by `updatedAt` rather than by arrival order. That is a rule instead of an accident, but it is not reconciliation, and for a resume position it probably should not be.
