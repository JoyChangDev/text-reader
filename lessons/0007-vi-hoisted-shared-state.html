Lesson 0007 · Shared Mutable Mock State

當兩個 vi.mock() 要共用同一份假資料：vi.hoisted()

目標：看懂 ticket 05（whole-book progressive generation orchestration，commit 530d4ac） 新增的 progressiveGeneration.test.js 裡為什麼要用 vi.hoisted()，然後獨立幫這個整合測試補一個還沒涵蓋的情境。

主要參考資料：Vitest — vi.hoisted() API 文件（官方文件）。 這篇說明為什麼需要它、它怎麼跟 vi.mock() 的提升時機配合。

先回憶一下 Lesson 0004 的提升（hoisting）

Lesson 0004 提過：vi.mock('路徑', factory) 會被 Vitest 提升到檔案最上面，比任何 import 都早執行。當時的例子裡，factory 自己造一個全新的假物件，不需要用到檔案裡其他地方宣告的變數： 

vi.mock('@/app/_lib/audioGenerationService', () => ({
  generateAudioForChunk: vi.fn(),
}));

但 progressiveGeneration.test.js 要做的事更複雜： 它要假造兩個外部依賴（@vercel/blob 和 edge-tts-universal）， 而且這兩個假模組要共用同一份「假資料庫」——一個記錄已上傳檔案的 Map，一個記錄呼叫過幾次 synthesize——這樣測試才能斷言「第二次呼叫沒有重新產生語音」。

直接宣告變數會壞掉

直覺的寫法可能是這樣：

// ❌ 這樣寫會噴 ReferenceError
const blobStore = new Map();

vi.mock('@vercel/blob', () => ({
  async get(pathname) {
    return blobStore.has(pathname) ? { stream: blobStore.get(pathname) } : null;
  },
  // ...
}));

問題出在提升的時機差一步：vi.mock() 整句（包括它的 factory）會被搬到檔案最上面， 但 const blobStore = new Map() 是一般的變數宣告，不會被提升——它還留在原本的位置。 等 Vitest 執行到被搬到最上面的 factory 時,blobStore 這一行根本還沒跑到, 變數只是宣告了但還沒被賦值（JS 稱為 temporal dead zone）。結果就是 ReferenceError: Cannot access 'blobStore' before initialization。

這跟 Lesson 0003/Lesson 0005 提過的陷阱是同一個家族：程式碼「看起來」該有的東西都在，但執行順序跟你想的不一樣。

解法：讓變數宣告跟著一起被提升

vi.hoisted(factory) 做的事很單純：把 factory 回傳的東西， 提早到跟 vi.mock() 同一個時間點準備好。progressiveGeneration.test.js 開頭： 

const { blobStore, synthesizeCalls } = vi.hoisted(() => ({
  blobStore: new Map(),
  synthesizeCalls: [],
}));

vi.mock('@vercel/blob', () => ({
  async get(pathname) {
    if (!blobStore.has(pathname)) return null;
    return { stream: blobStore.get(pathname) };
  },
  async put(pathname, data) {
    blobStore.set(pathname, typeof data === 'string' ? data : await data.text());
    return { url: `https://blob.test/${pathname}` };
  },
}));

vi.mock('edge-tts-universal', () => ({
  EdgeTTS: class {
    constructor(text) { this.text = text; }
    async synthesize() {
      synthesizeCalls.push({ text: this.text });
      return { audio: new Blob([`audio-for:${this.text}`]), subtitle: [{ text: this.text }] };
    }
  },
}));

因為 vi.hoisted() 本身也會被提升到最上面（而且比一般的 vi.mock() 更早）， 等到兩個 vi.mock() 的 factory 執行時，blobStore 和 synthesizeCalls 已經是「真正初始化過」的 Map 和陣列——兩個 mock 的 factory 讀寫的是同一份物件，這正是它們需要共用「假資料庫」的關鍵。

Lesson 0004 · vi.mock() 單獨用factory 自己造新假物件，不需要讀外部變數
今天 · vi.hoisted() + vi.mock()factory 需要讀寫檔案裡其他地方宣告的共用變數 → 那個變數也要提升

為什麼 beforeEach 要清空這兩個共用變數

blobStore 和 synthesizeCalls 是整個測試檔案共用、只建立一次的 Map/陣列——不會像 Lesson 0004 的 vi.fn() 那樣有 mockResolvedValueOnce 幫你限定只影響一次呼叫。如果不清空, 前一個測試存進 blobStore 的假錄音檔,會被下一個測試誤判成「快取已經有了」: 

beforeEach(() => {
  blobStore.clear();
  synthesizeCalls.length = 0;
});

跟 Lesson 0004 的 mockResolvedValueOnce 是同一種問題（共用狀態不重設,會漏到下一個測試), 只是這次共用的是原始的 Map/陣列,不是 vi.fn() 的回傳值隊列,所以解法是 beforeEach 手動清空,而不是 Once 版本的方法。

動手做 · 今天的目標

現在的三個測試都只用一本書驗證快取行為,從來沒驗證過:如果兩本不同的書 剛好在同一個 chunkIndex(例如都是 0)用一模一樣的文字,會不會被誤判成同一筆快取? 這其實是在鎖住 audioGenerationService.js 的快取 key 是 `${bookId}/${chunkIndex}/${voice}`,而不是只有 chunkIndex。

步驟:

  1. 開監看視窗:npm run test:watch progressiveGeneration。
  2. 在 progressiveGeneration.test.js 的 describe 區塊裡新增一個測試,名字取類似 'two different books do not share a cached chunk at the same index'。
  3. Arrange:一段固定的文字(例如 const text = '這是唯一的一句話。';),用 postChunks 拿到 chunks。
  4. Act:對 bookId: 'book-x' 呼叫一次 postAudioChunk({ bookId: 'book-x', chunkIndex: 0, text: chunks[0] }), 再對 bookId: 'book-y' 呼叫一次一模一樣的 chunkIndex: 0、 text: chunks[0]。
  5. Assert:synthesizeCalls 長度是 2(兩本書各自觸發一次真的生成, 不是第二次直接命中第一本書的快取)。
  6. 存檔確認測試變綠——不需要改 audioGenerationService.js,它的 cache key 本來就有帶 bookId,今天只是把這條行為鎖進測試套件。

這個測試會留在專案裡,跟其他三個一起保護 progressiveGeneration 的快取正確性——不是丟掉的練習題。 完成後記得自己 commit,跟過去幾課一樣。
