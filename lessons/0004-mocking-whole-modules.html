Lesson 0004 · Mocking a Whole Module

依賴注入不夠用的時候：用 vi.mock() 換掉整個模組

目標：看懂 ticket 04（Audio Generation Service）的 API route 測試裡已經用到的 vi.mock()，搞懂為什麼這裡不能用 Lesson 0003 的依賴注入， 然後獨立幫它多補一個還沒被涵蓋的邊界案例。

主要參考資料：Vitest — vi.mock() API 文件（官方文件）。 這篇說明 hoisting（提升）行為和 mock factory 的寫法；今天只挑 route.test.js 裡實際用到的部分講。

先恭喜一下：ticket 04 已經全部完成了

ticket 04 驗收清單上的六項，現在全部打勾了：真的 edge-tts Node 移植 （edgeTtsClient.js）、真的 Vercel Blob 持久化 （blobStorageClient.js）、cache hit/miss 邏輯， 還有一個真正的 API route（route.js）。 這些都已經合併進 feature/audio-generation 分支了。

但這個 route 的測試檔——route.test.js——用了一個 Lesson 0003 沒教過的技巧：vi.mock()。今天把這個補上。

新問題：這次沒有參數可以傳假物件

回想一下 Lesson 0003 的 getOrGenerateAudio：

export async function getOrGenerateAudio({ storageClient, ttsClient }, { ... }) {
  // storageClient、ttsClient 是參數 → 測試可以直接傳假物件進去
}

但 route.js 呼叫的是 generateAudioForChunk——ticket 04 刻意設計的「公開入口」， 固定用預設的 zh-TW 語音，不接受 client 參數： 

import { generateAudioForChunk } from '@/app/_lib/audioGenerationService';

export async function POST(request) {
  // ...
  const result = await generateAudioForChunk({ bookId, chunkIndex, text });
  // ...
}

route.js 在檔案頂端直接 import 它，呼叫的時候也沒有 storageClient/ttsClient 這種參數可以塞假的進去。 依賴注入這招在這裡用不上——測試需要一個新方法，能在不改 route.js 呼叫方式的前提下， 讓 generateAudioForChunk 變成假的。

解法：vi.mock() 把整條 import 路徑換掉

route.test.js 開頭是這樣寫的： 

import { generateAudioForChunk } from '@/app/_lib/audioGenerationService';

vi.mock('@/app/_lib/audioGenerationService', () => ({
  generateAudioForChunk: vi.fn(),
}));

const { POST } = await import('./route');

vi.mock(路徑, factory) 告訴 Vitest：「這個測試檔案裡，任何人 import 這個路徑，都給他 factory 回傳的假模組」——包括 route.js 自己在檔案頂端做的那個 import。它換掉的是整個模組，不是傳一個參數。

Hoisting（提升）：Vitest 會把 vi.mock() 呼叫提升到檔案最上面， 比任何 import 都早執行。這就是為什麼上面那段程式碼裡， 第一行先 import { generateAudioForChunk }，但實際拿到的已經是 mock 版本—— 因為等這行真正執行時，vi.mock() 早就先跑過了。也是為什麼最後用 const { POST } = await import('./route')（動態 import）而不是寫在檔案頂端： 確保 route.js 一定是在 mock 註冊完成之後才被載入、才會用到假的 generateAudioForChunk。

為什麼要用 mockResolvedValueOnce，不是 mockResolvedValue

這個檔案的三個測試共用同一個 generateAudioForChunk 假函式 ——它是 vi.mock() 在檔案載入時建立一次，不會在每個 test 之間自動重設 （這個專案的 vitest.config.js 沒有設定 clearMocks）。 如果第二個測試用 mockResolvedValue(persisted)（沒有 Once）， 這個回傳值會一直留著，變成第三個測試沒設定時的預設行為，可能讓「production 應該要失敗」的那個測試 意外收到一個成功結果。 

generateAudioForChunk.mockResolvedValueOnce(persisted);   // 只影響下一次呼叫
generateAudioForChunk.mockRejectedValueOnce(new Error(...)); // 用完就消失，不會留到下一個測試

經驗法則：同一個 mock 函式如果會被多個測試共用（尤其是 vi.mock() 這種模組層級的 mock）， 設定回傳值時預設就用 Once 版本，除非你確定要讓它一路延續到後面的測試。

動手做 · 今天的目標

route.test.js 裡的 400 測試只驗證了「缺少 text 欄位」， 但 route.js 的驗證邏輯是 !text——這代表空字串 text: '' 也應該被擋下來， 這個情況目前還沒有專屬的測試鎖住它。

步驟：

  1. 開監看視窗：npm run test:watch。
  2. 在 describe('POST /api/audio-chunks', ...) 區塊裡新增一個測試案例， 名字取類似 'rejects a request with an empty text string with 400'。
  3. 照現有 400 測試的樣子寫： Arrange 用 jsonRequest({ bookId: 'book-1', chunkIndex: 0, text: '' })； Act 呼叫 POST； Assert response.status 是 400，而且 generateAudioForChunk not.toHaveBeenCalled()。
  4. 存檔確認測試變綠——不需要改 route.js，這條行為它已經做對了， 今天只是把它鎖進測試套件裡。

這個測試會留在專案裡，跟其他兩個 route 測試一起保護 /api/audio-chunks 的驗證邏輯——不是丟掉的練習題。
