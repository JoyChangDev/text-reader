Lesson 0006 · RTL Fundamentals

第一次測「畫面」：render、screen、getByRole

目標：看懂這個專案從 ticket 01（測試基礎建設）就已經存在、但從來沒有一堂課解釋過的 page.test.jsx，搞懂 React Testing Library 怎麼「渲染」一個元件、 怎麼用 getByRole 找畫面上的東西，然後補一個 jest-dom 斷言，把它變得更扎實。

主要參考資料：Testing Library — React Testing Library 官方文件。 這篇文件的核心理念是：「你的測試越像使用者實際使用軟體的方式，就能給你越多信心」——今天會看到這句話具體長什麼樣子。

跟前五課不一樣的地方

Lesson 0001 到 Lesson 0005 測的都是「函式」—— formatDuration、chunkText、getOrGenerateAudio、 POST——呼叫它、檢查回傳值或有沒有呼叫某個假物件。沒有一堂課碰過「畫面」。

但 page.jsx 是一個 React 元件，不是一個可以直接呼叫拿到回傳值的函式。 它回傳的是 JSX——「畫面應該長什麼樣子」的描述，不是最終結果。要測「使用者會看到什麼」， 得先把這個描述變成真正的 DOM 元素，才有東西可以斷言。這正是今天的主角 render() 要做的事。

今天要看的程式碼

這個測試從這個專案第一次設定 Vitest（ticket 01）就已經存在，一直都在跑，只是還沒有一堂課 完整解釋過它在做什麼： 

import { render, screen } from '@testing-library/react';
import { expect, test } from 'vitest';

import ChakraProvider from './_providers/chakra';
import Home from './page';

test('renders the home page buttons', () => {
  render(
    <ChakraProvider>
      <Home />
    </ChakraProvider>,
  );

  expect(screen.getAllByRole('button', { name: 'Click me' })).toHaveLength(2);
});

對應的元件，page.jsx：

export default function Home() {
  return (
    <HStack bg="background" color="foreground">
      <Button>Click me</Button>
      <Button>Click me</Button>
    </HStack>
  );
}

render()：把元件變成真的 DOM

render(<Home />) 會把 Home 這個元件實際「掛載」到一個虛擬的文件（由 jsdom 提供，已經在 vitest.config.js 的 environment: 'jsdom' 設定好）裡，變成一棵真正的 DOM 樹——跟瀏覽器裡使用者會看到的結構一樣。 這裡額外包了一層 ChakraProvider，是因為 Home 用了 Chakra 的 <Button>/<HStack>，這些元件需要 Chakra 的 context 才能正確渲染—— 跟元件在真正的 app 裡被 layout.jsx 包起來的方式一樣。

這也是為什麼這個測試檔案的副檔名是 .jsx 而不是 .js——檔案裡直接寫了 JSX 語法 （<ChakraProvider><Home /></ChakraProvider>），需要 .jsx 讓建構工具正確解析。

screen 與 getByRole：找畫面上的東西

render() 執行完之後，畫面已經在虛擬 DOM 裡了，但測試要怎麼「看到」它？答案是 screen——一個綁定到目前渲染結果的查詢工具，上面掛了一整套 getBy.../ getAllBy... 方法。 

screen.getAllByRole('button', { name: 'Click me' })

這行的意思是：「找出畫面上所有 role 是 button、而且可存取名稱（accessible name） 是 'Click me' 的元素」。role 不是你自己標記的東西——瀏覽器和螢幕報讀軟體會自動 幫每個 HTML 元素推導出一個 role（<button> 就是 button， <h1> 就是 heading），getByRole 查的正是這個無障礙樹（accessibility tree），跟使用者用滑鼠點、或用螢幕報讀軟體聽到的是同一套資訊。

getByRole(role)找剛好一個符合的元素；找不到或找到超過一個都會讓測試失敗
getAllByRole(role)找所有符合的元素，回傳陣列——今天的例子用這個，因為畫面上有兩個按鈕
{ name: '...' }用可存取名稱（通常就是看得到的文字內容）再篩選一次

為什麼優先用 getByRole：依照 Testing Library 官方查詢優先順序， getByRole 排第一位，因為它逼你的測試用「使用者/無障礙工具找元素的方式」去找元素， 而不是憑你自己知道的內部結構（像 class name 或 DOM 巢狀層級）。如果 getByRole 真的找不到 合適的 role，才依序退到 getByLabelText、getByText，最後手段才是 getByTestId。

只找到東西還不夠：jest-dom matcher

toHaveLength(2) 只斷言「找到兩個元素」——但一個按鈕就算被 disabled， 一樣會被 getAllByRole('button') 找到。存在跟可以互動是兩件事。 這個專案已經裝了 @testing-library/jest-dom，並且在 vitest.setup.js 裡註冊好了，所以任何測試檔案都能直接用這些額外的 matcher， 不用再手動 import： 

expect(element).toBeInTheDocument()   // 元素真的在畫面上
expect(element).toBeEnabled()          // 元素不是 disabled，使用者按得下去
expect(element).toHaveTextContent('Hello')

跟 Lesson 0002 的 toBe/toEqual 是同一種東西（expect(x).matcher() 的形狀），只是這批 matcher 專門看「DOM 元素」， 不是看數字、字串或陣列。

動手做 · 今天的目標

現在的測試只鎖住了「畫面上有兩個叫 'Click me' 的按鈕」，但沒鎖住「這兩個按鈕使用者真的按得下去」。 如果之後有人不小心讓 Home 渲染出 disabled 的按鈕，這個測試現在完全不會發現。

步驟：

  1. 開監看視窗：npm run test:watch。
  2. 打開 page.test.jsx，在既有的 expect(...).toHaveLength(2) 斷言下面，把 getAllByRole 的結果存進一個變數，然後對其中每一個按鈕加上 expect(button).toBeEnabled()。
  3. 提示：getAllByRole(...) 回傳的是陣列，陣列有 .forEach可以用， 對每個元素各自斷言一次。
  4. 存檔確認測試變綠——不需要改 page.jsx，這條行為它本來就是對的， 今天只是把它鎖進測試套件裡。

這個測試會留在專案裡，跟 toHaveLength(2) 一起保護 Home 頁面——不是丟掉的練習題。
