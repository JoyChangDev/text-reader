Lesson 0008 · Shared Setup

用 beforeEach 收斂重複的 Arrange

目標：audioGenerationService.test.js 裡的四個測試, 每一個都手刻一次幾乎一樣的 storageClient/ttsClient 假物件。今天學會用 beforeEach 把「每個測試都要有」的部分收斂起來,只留下「這個測試特別在意」的部分, 然後親手把這個重構套用到真正的檔案上。

主要參考資料：Vitest — Test Hooks API 文件（beforeEach）（官方文件）。

先看看現在重複了什麼

audioGenerationService.test.js 目前有四個測試, 每一個的 Arrange 開頭都長這樣: 

const storageClient = {
  get: vi.fn()/* ...每個測試不同的行為 */,
  put: vi.fn()/* ...每個測試不同的行為 */,
};
const ttsClient = {
  synthesize: vi.fn()/* ...每個測試不同的行為 */,
};

還有呼叫 getOrGenerateAudio 時傳的第二個參數,四個測試裡完全一模一樣: 

{ bookId: 'book-1', chunkIndex: 0, voice: 'zh-TW-default', text: '你好。' }

真正因測試而異的,其實只有 storageClient.get/put 和 ttsClient.synthesize 各自 resolve/reject 什麼值——物件的骨架本身每次都一樣。

問題出在哪

骨架重複本身不會讓測試變紅,但代價是「改動成本」:如果 getOrGenerateAudio 的介面以後 多一個依賴(例如加一個 logger),就要記得去四個地方各補一次 logger: vi.fn()——漏改一個,那個測試看起來還是能跑,只是不小心少測到了新行為。 更麻煩的是,讀測試的人得先在腦中「消掉」四份幾乎相同的樣板,才找得到這個測試真正在斷言什麼。

beforeEach:每個測試之前都先跑一次

Vitest 的 beforeEach(fn) 註冊一個 hook,在同一個 describe 區塊裡, 每一個 test 開始前都會重新執行一次 fn。把共用的骨架搬進去, 兩個測試改寫後長這樣: 

import { beforeEach, describe, expect, test, vi } from 'vitest';

describe('getOrGenerateAudio', () => {
  let storageClient;
  let ttsClient;

  beforeEach(() => {
    storageClient = { get: vi.fn(), put: vi.fn() };
    ttsClient = { synthesize: vi.fn() };
  });

  test('returns the cached result without calling ttsClient on a cache hit', async () => {
    // Arrange：只設定這個測試在意的行為
    const cachedResult = { url: 'https://blob.example/cached.mp3', boundaries: [] };
    storageClient.get.mockResolvedValue(cachedResult);

    // Act
    const result = await getOrGenerateAudio(
      { storageClient, ttsClient },
      { bookId: 'book-1', chunkIndex: 0, voice: 'zh-TW-default', text: '你好。' },
    );

    // Assert
    expect(result).toEqual(cachedResult);
    expect(ttsClient.synthesize).not.toHaveBeenCalled();
  });

  test('calls ttsClient and persists the result on a cache miss', async () => {
    // Arrange
    const synthesized = {
      audio: new Blob(['fake-audio']),
      boundaries: [{ text: '你好', offset: 0, duration: 1000 }],
    };
    const persisted = { url: 'https://blob.example/generated.mp3', boundaries: synthesized.boundaries };
    storageClient.get.mockResolvedValue(undefined);
    storageClient.put.mockResolvedValue(persisted);
    ttsClient.synthesize.mockResolvedValue(synthesized);

    // Act
    const result = await getOrGenerateAudio(
      { storageClient, ttsClient },
      { bookId: 'book-1', chunkIndex: 0, voice: 'zh-TW-default', text: '你好。' },
    );

    // Assert
    expect(result).toEqual(persisted);
    expect(ttsClient.synthesize).toHaveBeenCalledWith('你好。', 'zh-TW-default');
    expect(storageClient.put).toHaveBeenCalledWith('book-1/0/zh-TW-default', synthesized);
  });
});

每個測試的 Arrange 現在只剩下「跟其他三個測試不一樣的那一行」,一眼就看得出這個測試在測什麼。

為什麼是 let + beforeEach 賦值,不是直接 const

storageClient/ttsClient 要在 describe 區塊裡宣告(這樣每個 test 才讀得到同一個名字),但**值**要在每個測試開始前重新建立——所以宣告 (let storageClient;)跟賦值(beforeEach 裡的 storageClient = {...}) 是分開兩步。如果直接在 describe 區塊裡用 const storageClient = {...}, 那份物件就只會建立一次,四個測試共用同一個 vi.fn()——第一個測試呼叫過 storageClient.get 之後,呼叫紀錄會留到第二個測試,污染 toHaveBeenCalledWith 之類的斷言。

跟 Lesson 0007 的 vi.hoisted() 對照

Lesson 0007 的 blobStore/synthesizeCalls 也是「跨測試共用」的狀態,但那次是刻意讓它們在整份檔案只建立一次(模擬一個持續存在的雲端儲存空間), 所以才需要 beforeEach 手動呼叫 blobStore.clear() 去清空。今天的 storageClient/ttsClient 目的完全相反:每個測試都該是全新、乾淨的假物件, 所以 beforeEach 裡做的是重新建立整個物件,而不是清空舊的——兩種寫法都用了 beforeEach,但解決的是相反方向的問題。

Lesson 0007 · vi.hoisted()狀態建立一次、跨測試共用 → beforeEach 負責清空
今天 · beforeEach 賦值狀態每個測試都要全新 → beforeEach 負責重建

動手做 · 今天的目標

把這個重構真正套用到 audioGenerationService.test.js 上, 四個測試全部改完,不是只改上面示範的兩個。

步驟：

  1. 開監看視窗：npm run test:watch audioGenerationService。
  2. 從 vitest 多 import 一個 beforeEach。
  3. 在 describe('getOrGenerateAudio', ...) 區塊最上面宣告 let storageClient; 和 let ttsClient;,接著加上本課示範的 beforeEach,建立兩個乾淨的假物件。
  4. 把四個測試裡重複的 const storageClient = {...}/const ttsClient = {...} 都刪掉,改成直接對共用變數呼叫 .mockResolvedValue(...)/.mockRejectedValue(...)。
  5. 剩下兩個「失敗路徑」的測試(propagates the error... 開頭那兩個)也要照著改——它們一樣有 重複的假物件骨架。
  6. 存檔確認四個測試都還是綠的——這個重構不改變任何斷言,只是把重複的 Arrange 收斂掉。

這個重構會留在專案裡,讓 audioGenerationService.test.js 之後更容易讀、更容易加新測試——不是丟掉的練習題。 完成後記得自己 commit,跟過去幾課一樣。
