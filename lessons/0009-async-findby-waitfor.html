Lesson 0009 · Async UI

非同步 UI：findBy 與 waitFor

目標：Ticket 06（上傳＋漸進式播放 UI）已經完工，BookUploader.test.jsx 裡已經有真正在用 findBy/waitFor 的測試——只是還沒有一堂課解釋過它們。這是 MISSION.md 清單上最後一項還沒教的技能：測試「讀取中 → 成功/失敗」這種非同步 UI 行為。 今天看懂這些既有測試，然後親手幫 BookUploader 補一個目前沒人測到的真實情境。

主要參考資料：Testing Library — Async 工具官方文件（findBy、waitFor）。

為什麼 getByText 在這裡不夠用

Lesson 0006 學過的 getByRole/getByText 是同步的——呼叫當下畫面上有沒有這個元素，馬上就有答案。但 BookUploader 選了檔案之後, 真正的畫面更新要等 fetch('/api/chunks') 這個 Promise resolve 之後才會發生： 

fireEvent.change(input, { target: { files: [file] } });

// 這裡執行的當下，fetch 可能還沒 resolve，錯誤訊息可能還沒出現在畫面上
expect(screen.getByText(/couldn't process/i)).toBeInTheDocument(); // ❌ 常常會失敗

問題不是邏輯錯了，是時機錯了：斷言執行的那一刻,非同步更新可能還沒發生。需要的是一個 「先等,等到出現（或等到超時）再判斷」的查詢方式。

findBy*：會等待的 getBy*

這正是專案裡已經存在的這個測試在做的事——BookUploader.test.jsx 「檔案處理失敗時顯示錯誤訊息」那個測試： 

test("shows an error message if chunking the uploaded file fails", async () => {
  global.fetch = vi.fn(
    async () => new Response(JSON.stringify({ error: 'nope' }), { status: 400 }),
  );
  const onReady = vi.fn();

  render(<ChakraProvider><BookUploader onReady={onReady} /></ChakraProvider>);

  const file = makeTxtFile('第一段。');
  const input = screen.getByLabelText(/upload/i);
  fireEvent.change(input, { target: { files: [file] } });

  expect(await screen.findByText(/couldn't process/i)).toBeInTheDocument();
  expect(onReady).not.toHaveBeenCalled();
});

screen.findByText(...) 回傳一個 Promise：它會每隔一小段時間重新查詢一次畫面, 直到找到符合的元素、或超過預設的 1000ms timeout 才放棄（timeout 就會 reject,測試失敗並附上目前的 DOM 內容方便除錯）。 前面加 await,拿到的就是真的找到的那個元素——所以才能直接對它呼叫 .toBeInTheDocument()。

心法：findByText(x) 幾乎等於「不斷重試 getByText(x), 抓到就回傳,逾時就放棄」。find 這個字首本身就是在提示你「這需要花時間找」。

waitFor：等一個任意斷言成立

findBy* 只能用來等「某個元素出現」。但同一個測試檔案裡,「成功上傳」的那個測試要等的不是畫面上多了什麼元素, 而是一個假函式有沒有被呼叫——這種情況换用 waitFor： 

fireEvent.change(input, { target: { files: [file] } });

await waitFor(() => expect(onReady).toHaveBeenCalledTimes(1));

const [book] = onReady.mock.calls[0];
expect(book.chunks).toEqual(['第一段。', '第二段。']);

waitFor(callback) 會不斷重複執行 callback,只要裡面的 expect(...) 還在拋錯就繼續重試,直到它不再拋錯（成功）或超過 timeout（失敗）才停下來。findBy* 其實就是 「查詢＋waitFor」包在一起的語法糖,專門處理「等元素出現」這一種情況；碰到「等一個不是『元素存不存在』 的條件」（呼叫次數、某個值變了……),就直接用更通用的 waitFor。

getByText(x)同步,馬上查;找不到就拋錯讓測試失敗
queryByText(x)同步,馬上查;找不到回傳 null（不拋錯）
findByText(x)非同步,重試查詢直到找到或逾時;回傳 Promise,要 await
waitFor(cb)非同步,重試任意 cb 直到不拋錯或逾時;比 findBy* 更通用

陷阱：用 findBy 斷言「東西不見了」會很慢

findBy* 是為了「等某個東西出現」設計的,如果拿它去確認「某個東西沒出現」,會等到整個 timeout 跑完才判斷失敗（或成功）——白白拖慢測試。確認「沒有」要用同步、找不到只回傳 null 的 queryBy*。AudioPlayer.test.jsx 裡就有這個對照組——錯誤狀態出現時,順便確認「Play 按鈕沒有跟著顯示」： 

expect(await screen.findByRole('alert')).toHaveTextContent(/couldn't generate audio/i);
// 錯誤已經確定出現了，這裡不需要再「等」——直接同步查詢有沒有
expect(screen.queryByRole('button', { name: /^play$/i })).not.toBeInTheDocument();

經驗法則：「等它出現」→ findBy；「確認它不在」→ queryBy + .not.toBeInTheDocument()；「等一個不是元素存在與否的條件」→ waitFor。

動手做 · 今天的目標

BookUploader.jsx 的 processFile 一開始就呼叫 setError(null)——也就是說,如果讀者先上傳一個失敗的檔案（畫面出現錯誤訊息）,接著再成功上傳另一個檔案, 舊的錯誤訊息應該會消失。這個行為目前完全沒有測試覆蓋——去補上它。

步驟：

  1. 開監看視窗：npm run test:watch BookUploader。
  2. 在 BookUploader.test.jsx 裡新增一個測試: 「成功上傳新檔案後,先前的錯誤訊息會消失」。
  3. 先讓 global.fetch 回傳失敗（跟現有的錯誤測試一樣的寫法）,上傳一個檔案,用 findByText 確認錯誤訊息真的出現了。
  4. 接著把 global.fetch 換成回傳成功的版本,再對同一個 input 觸發一次 fireEvent.change（上傳第二個檔案）。
  5. 用 waitFor 確認 onReady 這次真的被呼叫了一次——代表第二次上傳成功處理完了。
  6. 最後用 queryByText（不是 findByText！)確認錯誤訊息已經不在畫面上了。
  7. 存檔確認新測試變綠,其他測試也還是綠的。

這個測試會留在 BookUploader.test.jsx 裡,補上一個真實存在但目前沒人測到的行為——不是丟掉的練習題。 完成後記得自己 commit,跟過去幾課一樣。
