Lesson 0005 · Async Rejection

測試一個會失敗的 async 函式：rejects.toThrow()

目標：看懂 commit ebb65cf（feat(audio): wire real edge-tts and Vercel Blob into the generation service）裡新增的「生成失敗」測試，學會 toThrow（Lesson 0002 教過的同步版本）在 async 函式上為什麼不能直接用，然後獨立幫一個還沒被涵蓋的失敗情境補一個測試。

主要參考資料：Vitest — expect().rejects 文件（官方文件）。 這篇說明 rejects 怎麼「打開」一個 Promise 的失敗結果，讓後面接的 matcher（像 toThrow）可以斷言它。

這次要看的程式碼

commit ebb65cf 把真的 edge-tts 和 Vercel Blob 接進 audioGenerationService.js，也在 audioGenerationService.test.js 補了一個新測試： 如果 edge-tts 生成失敗，會發生什麼事？ 

test('propagates the error and does not persist anything when generation fails', async () => {
  // Arrange
  const storageClient = {
    get: vi.fn().mockResolvedValue(undefined),
    put: vi.fn(),
  };
  const ttsClient = {
    synthesize: vi.fn().mockRejectedValue(new Error('edge-tts request failed')),
  };

  // Act / Assert
  await expect(
    getOrGenerateAudio(
      { storageClient, ttsClient },
      { bookId: 'book-1', chunkIndex: 0, voice: 'zh-TW-default', text: '你好。' },
    ),
  ).rejects.toThrow('edge-tts request failed');
  expect(storageClient.put).not.toHaveBeenCalled();
});

為什麼不能直接用 Lesson 0002 的 toThrow

Lesson 0002 提過 expect(fn).toThrow()：呼叫 fn，如果它同步地拋出錯誤，斷言就通過。 直覺可能會想照樣寫： 

// ❌ 這樣寫是錯的，而且不會告訴你哪裡錯
expect(() => getOrGenerateAudio({ storageClient, ttsClient }, { ... })).toThrow();

這行不會照你想的方式失敗（也不會照你想的方式成功）。原因是 getOrGenerateAudio 是 async 函式：呼叫它永遠立刻回傳一個 Promise， 不會同步拋出任何東西——就算 ttsClient.synthesize 最後會 reject，那也是之後才發生的事， 跟「呼叫當下有沒有同步拋錯」是兩件事。toThrow 只看得到「呼叫當下」，看不到「之後才 reject」。

這跟 Lesson 0003 提過的 test.todo 陷阱是同一種類型的坑： 程式碼「看起來」在測某件事，實際上斷言根本沒發生在對的時間點，而且不會報錯提醒你。

正確寫法：await expect(promise).rejects.toThrow(...)

把「呼叫函式拿到的 Promise」直接交給 expect()，再串上 .rejects， 告訴 Vitest「等這個 Promise 解決，然後把它 reject 的錯誤，交給後面的 matcher 斷言」： 

await expect(
  getOrGenerateAudio({ storageClient, ttsClient }, { ... }),
).rejects.toThrow('edge-tts request failed');
expect(fn).toThrow()同步函式：呼叫的當下就要拋出錯誤（Lesson 0002）
await expect(promise).rejects.toThrow(msg)async 函式：等 Promise reject，斷言錯誤訊息（今天）

外層的 await 不能漏掉——沒有它，測試在 Promise 真正 reject 之前就已經跑完了， 斷言可能根本來不及執行（跟 Lesson 0003 的 test.todo 一樣，是個「安靜地什麼都沒測到」的陷阱）。

別搞混：mockRejectedValue vs rejects.toThrow

這個測試裡有兩個長得像、但做完全不同事情的東西：

  • ttsClient.synthesize: vi.fn().mockRejectedValue(new Error(...)) ——設定假物件：假的 synthesize 被呼叫時要 reject 成什麼錯誤。
  • expect(getOrGenerateAudio(...)).rejects.toThrow(...) ——斷言被測函式本身（getOrGenerateAudio）回傳的 Promise 有沒有正確地把這個錯誤傳出來。

一個是「餵給假物件的輸入」，一個是「驗證真正程式碼的輸出」——這正是這個測試想確認的事： getOrGenerateAudio 沒有用 try/catch 把錯誤吞掉，而是讓它繼續往外傳。 也因為這樣，最後一行 expect(storageClient.put).not.toHaveBeenCalled() 才成立： 生成失敗，就不該有東西被存進快取。

動手做 · 今天的目標

上面這個測試只涵蓋了「ttsClient.synthesize 失敗」的情況。但 getOrGenerateAudio 最後一步是 storageClient.put——如果它失敗 （例如 Vercel Blob 上傳失敗），目前完全沒有測試鎖住這個情境。

步驟：

  1. 開監看視窗：npm run test:watch。
  2. 在 audioGenerationService.test.js 裡新增一個測試， 名字取類似 'propagates the error when persisting the generated audio fails'。
  3. Arrange：storageClient.get 一樣 mockResolvedValue(undefined)（cache miss）； ttsClient.synthesize 正常成功，mockResolvedValue 一個你自己編的假生成結果； 但這次 storageClient.put 用 mockRejectedValue(new Error('blob upload failed'))。
  4. Act/Assert：跟上面範例同樣的寫法， await expect(getOrGenerateAudio(...)).rejects.toThrow('blob upload failed')。
  5. 存檔確認測試變綠——不需要改 audioGenerationService.js， 它本來就沒有吞掉錯誤，今天只是把這條路徑也鎖進測試套件。

這個測試會留在專案裡，跟其他三個 getOrGenerateAudio 測試一起涵蓋 cache hit、cache miss、 生成失敗、還有現在這條持久化失敗——不是丟掉的練習題。
