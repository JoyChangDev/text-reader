Lesson 0003 · Fakes at a Boundary

用假物件測試一個「邊界」：vi.fn() 與依賴注入

目標：學會怎麼在測試裡「替換掉」一個模組會呼叫的外部依賴（網路、儲存空間）， 然後把這個技巧用在 ticket 04（Audio Generation Service）真正的程式碼上。

主要參考資料：Vitest — Mock Functions API（官方文件）。 這篇涵蓋 vi.fn() 的完整用法；今天只挑今天會用到的 mockResolvedValue 和 toHaveBeenCalledWith 講。

先收個尾 · 2 分鐘暖身

在進新東西之前，先把 Lesson 0002 留下的尾巴接上： 幫 chunkText.test.js 補上 chunkText('') 應該回傳空陣列 [] 的測試（用 toEqual，不是 toBe — 還記得為什麼嗎？）。這是刻意的複習，不是新內容。寫完再往下讀。

為什麼 toBe/toEqual 還不夠

Lesson 0001 和 Lesson 0002 測的都是「純函式」—— 給定輸入，回傳輸出，沒有任何副作用。formatDuration 和 chunkText 都是這樣。

但 ticket 04 的 Audio Generation Service 不是純函式 —— 它要呼叫 edge-tts（真的網路請求）和物件儲存空間（真的雲端服務）。 如果測試真的打這些請求，會很慢、不穩定（今天過、明天可能因為網路問題失敗），而且會產生真的費用。 這正是 MISSION.md 裡點名的那個模式： 「能在模組邊界替換掉假物件/mock，讓測試永遠不會真的打網路請求。」

解法：依賴注入 + 假物件

看一下已經幫你寫好的 audioGenerationService.js： 

export async function getOrGenerateAudio({ storageClient, ttsClient }, { bookId, chunkIndex, voice, text }) {
  const key = cacheKey({ bookId, chunkIndex, voice });

  const cached = await storageClient.get(key);
  if (cached) {
    return cached;
  }

  const generated = await ttsClient.synthesize(text, voice);
  await storageClient.put(key, generated);
  return generated;
}

注意 storageClient 和 ttsClient 是參數，不是在檔案頂端 import 進來的。 這個寫法叫依賴注入（dependency injection）：函式不自己決定要用哪個真的 client，而是由呼叫它的人（正式環境的 API route，或測試）決定要傳什麼東西進去。

這正是 ticket 04 驗收清單上的那一條：「the edge-tts client and storage client are not called from anywhere else」—— 依賴注入就是達成「單一邊界」的具體做法。之後 API route 會傳真的 client 進來；測試會傳假的進去。函式本身完全不知道差別。

「假的」client 長什麼樣？就是一個形狀對得上的普通物件，方法用 vi.fn() 建立： 

const storageClient = {
  get: vi.fn().mockResolvedValue(cachedResult), // 呼叫時回傳一個 Promise，resolve 成 cachedResult
  put: vi.fn(),                                  // 呼叫時什麼都不用回傳
};
const ttsClient = {
  synthesize: vi.fn(),
};
vi.fn()建立一個假函式，可以被呼叫、記錄「有沒有被呼叫、被什麼參數呼叫」
.mockResolvedValue(x)呼叫這個假函式時，回傳一個 resolve 成 x 的 Promise（給 async 函式用）
.mockReturnValue(x)呼叫這個假函式時，直接回傳 x（同步、非 Promise 的情況用這個）
expect(fn).toHaveBeenCalledWith(...)斷言這個假函式有被呼叫過，而且參數符合預期
expect(fn).not.toHaveBeenCalled()斷言這個假函式從頭到尾沒被呼叫過

讀一個完整案例：cache hit

audioGenerationService.test.js 裡已經有一個寫好的測試， 測「快取已經有這個 chunk」的情況： 

test('returns the cached result without calling ttsClient on a cache hit', async () => {
  // Arrange
  const cachedResult = { url: 'https://blob.example/cached.mp3', boundaries: [] };
  const storageClient = {
    get: vi.fn().mockResolvedValue(cachedResult),
    put: vi.fn(),
  };
  const ttsClient = {
    synthesize: vi.fn(),
  };

  // Act
  const result = await getOrGenerateAudio(
    { storageClient, ttsClient },
    { bookId: 'book-1', chunkIndex: 0, voice: 'zh-TW-default', text: '你好。' },
  );

  // Assert
  expect(result).toEqual(cachedResult);
  expect(ttsClient.synthesize).not.toHaveBeenCalled();
});

注意兩件事：第一，test 的回呼函式是 async，因為 getOrGenerateAudio 回傳 Promise， 要用 await 才能拿到真正的結果。第二，最後一個斷言不是在測「回傳值對不對」， 而是在測「ttsClient.synthesize 完全沒被呼叫」—— 這就是 cache hit 的重點： 快取有東西的話，不應該再去呼叫 edge-tts。

動手做 · 今天的目標

打開 audioGenerationService.test.js， 把 test.todo('calls ttsClient and persists the result on a cache miss') 換成一個真正的測試。

要測的情境：快取沒有這個 chunk（storageClient.get resolve 成 undefined）， 應該發生什麼事？

  1. 開監看視窗：npm run test:watch。
  2. Arrange：這次 storageClient.get 要 mockResolvedValue(undefined)； ttsClient.synthesize 要 mockResolvedValue(生成的結果)（自己決定一個假的 { url, boundaries } 物件）； storageClient.put 保留原樣的 vi.fn() 就好。
  3. Act：跟上面的例子一樣呼叫 getOrGenerateAudio。
  4. Assert 三件事：
    • 回傳值等於你 mock 的生成結果（toEqual）。
    • ttsClient.synthesize 有被呼叫，而且參數是 (text, voice)（toHaveBeenCalledWith）。
    • storageClient.put 有被呼叫，把生成結果存進快取（toHaveBeenCalledWith，key 是 `${bookId}/${chunkIndex}/${voice}`）。

這個檔案是真的專案程式碼，不是丟掉的練習 —— 它就是 ticket 04 驗收清單上 「Unit tests exercise the service module's behavior (cache hit, cache miss, generation failure)」 這條的前兩項。真正的 edge-tts 移植和 Vercel Blob 串接還沒做，之後才會接上； 今天先把「快取邏輯本身是對的」這件事鎖住。
