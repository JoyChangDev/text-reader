Vitest 基礎速查表

來自 Lesson 0001、Lesson 0002 與 Lesson 0003 的精華，供之後隨時查閱。

執行測試

npm run test         # 監看模式，改檔案自動重跑
npm run test -- run  # 或用 package.json 裡的 "test" script 跑一次就結束

這個專案的 package.json 已經把 npm test 設成 vitest run（跑一次），npm run test:watch 設成監看模式。

測試檔案的骨架

import { describe, expect, test } from 'vitest';

describe('某個功能', () => {
  test('在某種情況下應該怎樣', () => {
    // Arrange 準備
    // Act    執行
    // Assert 斷言
  });
});
  • describe — 把相關的測試分組，純粹是給人看的組織單位，非必要。
  • test（別名 it）— 一個獨立的測試案例，描述文字要說清楚「在什麼情況下、預期什麼結果」。
  • expect — 斷言 API 的入口，後面接一個 matcher。

AAA 模式

Arrange準備輸入、初始狀態
Act執行你要測試的那一個行為
Assert斷言結果符合預期

常用 Matchers（純函式 / 邏輯）

expect(value).toBe(3)                  // 嚴格相等（===），數字、字串、布林用這個
expect(obj).toEqual({ a: 1 })          // 深層相等，物件、陣列用這個 —— 不要用 toBe！
expect(fn).toThrow()                   // 呼叫 fn 時應該拋出錯誤
expect(array).toHaveLength(2)          // 陣列/字串長度
expect(str).toMatch(/[。！？]$/)        // 字串符合正規表達式（格式對不對）
expect(n).toBeGreaterThan(0)           // 數字大於
expect(n).toBeLessThanOrEqual(20)      // 數字小於等於（上限用這個）

toBe vs toEqual：陣列/物件即使內容相同也不是同一個記憶體位置， toBe 會誤判失敗。經驗法則：原始值（數字/字串/布林）用 toBe，陣列/物件一律用 toEqual。 來自 Lesson 0002。

常用 Matchers（React Testing Library，來自 jest-dom）

expect(element).toBeInTheDocument()
expect(element).toBeDisabled()
expect(element).toHaveTextContent('Hello')

這些是 @testing-library/jest-dom 提供的擴充 matcher，已經在這個專案的 vitest.setup.js 裡註冊好了，不用額外 import。

假物件與依賴注入（Mocking）

const storageClient = {
  get: vi.fn().mockResolvedValue(cachedResult), // async 函式回傳值 → mockResolvedValue
  put: vi.fn(),                                  // 不用管回傳值，就留空
};

expect(ttsClient.synthesize).not.toHaveBeenCalled();          // 完全沒被呼叫
expect(storageClient.put).toHaveBeenCalledWith(key, value);   // 有被呼叫，而且參數對
  • vi.fn() — 建立一個假函式，記錄呼叫次數與參數。
  • .mockResolvedValue(x) — 呼叫時回傳 resolve 成 x 的 Promise（async 函式用這個）。
  • .mockReturnValue(x) — 呼叫時直接回傳 x（同步函式用這個）。

依賴注入：把外部依賴（edge-tts client、儲存空間 client）當函式參數傳入， 而不是在檔案頂端 import，測試才能用假物件替換掉它們，不會打真的網路請求。 來自 Lesson 0003，範例見 audioGenerationService.js。

整個模組換成假的（vi.mock()）

import { generateAudioForChunk } from '@/app/_lib/audioGenerationService';

vi.mock('@/app/_lib/audioGenerationService', () => ({
  generateAudioForChunk: vi.fn(),
}));

const { POST } = await import('./route'); // 動態 import，確保在 mock 註冊後才載入

// ...在個別測試裡：
generateAudioForChunk.mockResolvedValueOnce(persisted);
generateAudioForChunk.mockRejectedValueOnce(new Error('...'));
  • vi.mock(路徑, factory) — 讓這個測試檔案裡任何 import 該路徑的地方（包括被測檔案自己）都拿到假模組。
  • Hoisting：vi.mock() 會被提升到檔案最上面，比 import 都早執行。
  • 用 mockResolvedValueOnce/mockRejectedValueOnce，不是不加 Once 的版本——同一個 mock 函式被多個測試共用，沒加 Once 的設定會留到下一個測試（這個專案沒設定 clearMocks）。

依賴注入（Lesson 3） vs vi.mock()（Lesson 4）： 函式把依賴當「參數」接收時，用依賴注入直接傳假物件；函式在檔案頂端直接 import 依賴、沒有參數可傳時，用 vi.mock() 換掉整個模組。 範例見 route.test.js。

測試 async 函式的失敗（rejects.toThrow）

// ❌ 不會照你想的方式運作：async 函式呼叫當下不會同步拋錯
expect(() => someAsyncFn()).toThrow();

// ✅ 正確寫法：await + rejects
await expect(someAsyncFn()).rejects.toThrow('錯誤訊息');
  • expect(fn).toThrow() — 同步函式：呼叫當下就要拋錯（Lesson 0002）。
  • await expect(promise).rejects.toThrow(msg) — async 函式：等 Promise reject，斷言錯誤訊息（Lesson 0005）。
  • 外層 await 不能漏——沒有它，測試可能在 Promise 真正 reject 之前就跑完了。

別搞混：vi.fn().mockRejectedValue(err) 是設定「假物件」要 reject 什麼； expect(promise).rejects.toThrow(msg) 是斷言「被測函式」有沒有正確把錯誤傳出來——一個是輸入，一個是輸出。 範例見 audioGenerationService.test.js。

⚠️ test.todo 的陷阱

test.todo('之後要寫的測試', async () => {
  expect(true).toBe(false); // 這一行永遠不會被執行！
});

test.todo 就算傳了 callback 進去也不會執行它——它的用途是先佔位、 標記「這個測試之後要補」，不是拿來寫真正的測試內容。npm test 會顯示 1 passed | 1 todo，不會報錯、也不會失敗，所以斷言沒被執行這件事很容易被忽略。 要讓測試真的跑，把 test.todo( 換成 test( 就好。

查詢優先順序（RTL）

依照 Testing Library 官方優先順序，由上到下優先使用：

  1. getByRole — 最優先，貼近使用者/無障礙工具怎麼找元素
  2. getByLabelText / getByPlaceholderText — 表單元素
  3. getByText — 非互動的文字內容
  4. getByTestId — 最後手段，前面都不適用時才用
